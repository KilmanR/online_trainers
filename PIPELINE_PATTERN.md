# Универсальный алгоритм «фоновой задачи с ролями» (не привязан к контенту)

Рабочая схема, отлаженная на проекте Tattoo_Study_Base. Применима к любому
длинному фоновому сбору/обработке на сервере. Семь шагов.

## 1. TODO / план
- Разбить на этапы и прописать в список задач (todo-лист), один текущий.
- У каждого этапа — понятный критерий «сделано» (маркер финала).

## 2. Roadmap
- Таблица этапов со статусами: ✅ завершено / ▶️ идёт / ⏳ дальше / ⚠ проблема.
- Хранить в человеко-читаемом виде (SYSTEM_OVERVIEW или README).

## 3. Пайплайн с разделением ролей (самое важное)
- **Оркестратор (главный агент):** планирует, пишет код, запускает, проверяет, решает.
- **Код/скрипты:** вся детерминированная логика (подсчёты, классификация статусов,
  скачивание, обработка). Никогда не отдавать это модели.
- **Малая локальная модель (1–7B):** ТОЛЬКО генерация текста/пересказ готового
  вывода. Никакой классификации и фактов — она их путает.
- **Инструкции модели — на её родном/сильном языке** (напр., китайская qwen
  обучена в основном на англ. — «как делать» даём на англ., ответ просим
  по-русски). Инструкций на русском слабые модели понимают хуже.
- Формула: *код считает факты → код формирует детерминированный вывод →
  модель его пересказывает*.
- В файл-отчёт всегда кладём и «точный вывод (от кода)», и «рассказ модели» —
  для сверки.

## 4. Устойчивость фонового запуска
- Запуск: `setsid nohup … >log 2>&1 </dev/null &` — переживает отвал ssh.
- Бейся против «зависания»: логи с `flush=True`, прогресс построчно.
- Маркеры завершения в финальной строке (`# DONE`, «готово: N …») — их ищет монитор.
- Докачка/пропуск уже готового (idempotent), паузы и ретраи при лимитах (429 и т.п.).
- Ограничение скорости (--rate) — жалеть диск и источник.

## 5. Наблюдение и алерты
- Монитор-сторож в cron (раз в 10 мин): процесс жив? лог растёт? маркер завершения?
- Статусы: идёт / завершено / ⚠ возможно зависло (лог не растёт N мин).
- Отчёты: файл статусов + файл «рассказа» от модели (её и читают).
- Лог событий («ЗАВЕРШЕНА …»), событие пишется один раз (state.json).
- Push к человеку: **переиспользовать уже существующий алерт** (напр., `send_vk()`
  из zen_health/temp_monitor.py), не писать свой с нуля.

## 6. QA перед финалом
- Дождаться полного завершения → проверить папки/файлы, выборочно открыть результат.
- Поправить косяки (напр., мусор OCR), при необходимости перегнать этап.
- Протестировать канал оповещения тестовым сообщением.

## 7. Финал: хранение и легальность
- Решить, куда заливать (объём, условия, лимиты бесплатных тарифа).
- Проверить, что всё собрано только из легальных источников (личное некоммерческое
  использование; закрытые материалы — только ссылками, не ломать).
- Бэкап важного перед любым «разрушительным» шагом (переустановка/чистка).
